== Rendimiento

* El bucle de juego debe mantener una actualización estable; se acepta una tasa mínima de 30 fps en móviles de gama media.
* La carga inicial debe priorizar el contenido esencial de la pantalla de inicio y diferir assets secundarios cuando sea posible.
* Las imágenes deben usar el tamaño y formato adecuados para TIC-80 y para la PWA; se prefieren sprites pequeños y paletas limitadas.
* El audio debe cargarse de forma que no bloquee la primera interacción.
* El service worker debe cachear solo los recursos necesarios para una partida completa, evitando un caché inicial excesivo.

== Usabilidad

* La interfaz debe comunicar el estado del juego en todo momento: ave activa, turno, HP, PP y resultado.
* Las acciones destructivas o que cambian el rumbo de la partida (rendirse) deben requerir confirmación.
* Los mensajes de error deben explicar qué ocurrió y cómo continuar.
* El jugador no debe necesitar leer documentación externa para completar una partida.
* Los íconos PPTLS deben ir acompañados de texto o forma para no depender solo del color.

== Accesibilidad

* Contraste mínimo de 4.5:1 para texto normal y 3:1 para texto grande.
* Foco visible en todos los elementos interactivos.
* Navegación completa por teclado en escritorio.
* Control de silencio persistente durante la sesión.
* Alternativa textual para los íconos y resultados de cada turno.
* No usar animaciones parpadeantes ni efectos que puedan causar molestias.
* Tamaño de fuente legible en móvil y opción de texto claro en las descripciones.

== Seguridad y privacidad

* El juego no recopila datos personales.
* No se usan cookies de seguimiento ni servicios de analítica de terceros en el MVP.
* No se incluyen claves, tokens ni secretos en el repositorio.
* Los recursos externos se sirven por HTTPS.
* Las dependencias de desarrollo se mantienen actualizadas y auditadas.
* El código no ejecuta contenido de terceros no confiable.

== Mantenibilidad

* El código JavaScript se organiza en módulos con responsabilidades claras: escenas, estado, batalla, datos y audio.
* La lógica de batalla debe ser independiente de la interfaz para permitir pruebas unitarias.
* Se usa un linter y un formato consistentes.
* Las funciones críticas (HP, PP, daño, PPTLS, fin de batalla) tienen pruebas automatizadas.
* Los cambios relevantes se registran en un ADR o en el changelog.
* El repositorio incluye un README con pasos de instalación, build y despliegue.

== Portabilidad y despliegue

* El build debe funcionar en un entorno limpio con Node.js y las dependencias declaradas.
* El workflow de GitHub Actions debe ser la fuente de verdad del proceso de build.
* La configuración de rutas debe funcionar en GitHub Pages (incluido el subdirectorio del repositorio).
* El despliegue debe poder revertirse a una versión anterior mediante tags o releases.
* El juego y la documentación se publican como artefactos estáticos.

== Licencias y créditos

* Las imágenes, música y efectos deben ser creados por el equipo o tener licencia compatible con la publicación pública.
* Se debe mantener un archivo `CREDITS.md` con autoría y licencia de cada recurso.
* Los datos científicos de las aves deben citar la fuente utilizada.
* El nombre del juego y los nombres de movimientos no deben infringir marcas registradas de terceros.
* La documentación se publica bajo CC BY 4.0 y el código bajo la licencia elegida por el equipo.

== Disponibilidad y soporte

* La URL pública debe estar disponible durante el periodo de evaluación y al menos 30 días después del lanzamiento.
* Los errores críticos deben tener un canal de reporte definido en el README.
* Se debe documentar cómo reproducir el entorno de desarrollo.
* El equipo debe conservar una copia de los assets originales para futuras correcciones.
